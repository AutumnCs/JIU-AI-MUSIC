# 后端与登录方案

> 当前版本：当前建议版
> 基准日期：2026-08-03

## 1. 目标

先把 Jiu 的“游客模式”跑通，形成一套最小但完整的账号体系：

- 用户第一次进入时自动获得一个稳定身份
- 作品、进度、收藏等数据可以挂到这个身份上
- 现有前端的本地状态不需要推倒重来
- 后续可以平滑升级为邮箱登录，而不是重新设计一套账户系统

## 2. 现状判断

当前项目已经有一层本地游客态：

- `jiu-app/stores/globalStore.ts` 里会在本地生成 `jiu_user_id`
- `jiu-app/stores/globalStore.ts` 会把大部分状态写入 `localStorage`
- `jiu-app/app/layout.tsx` 负责初始化和 onboarding

这说明现在的核心问题不是“有没有账号”，而是：

- 账号只存在于浏览器本地
- 换设备、清缓存、重新安装后身份会丢
- 后续一旦接邮箱登录，当前本地游客态需要有升级路径

所以这一版不做完整认证系统，只做“游客身份 + 会话 + 数据归属”的最小闭环。

## 3. 设计原则

- 先让用户能用，再让用户登录
- 先做游客身份，再做正式账号
- 先保留本地状态，再逐步迁移到云端
- 接口要足够薄，避免一开始就把后端做重
- 账号体系要可升级，游客身份以后能并入邮箱账号

## 4. 推荐方案

### 方案 A：纯前端游客态

优点：

- 最快
- 不需要后端

缺点：

- 只能留在当前浏览器
- 数据容易丢
- 后面加登录时重构成本高

### 方案 B：本地游客 + 轻后端

优点：

- 保留当前前端体验
- 后端只负责身份和会话，复杂度低
- 后续接邮箱登录最顺

缺点：

- 需要补一个最小后端
- 需要一个数据库存用户和会话

### 方案 C：直接完整登录体系

优点：

- 一步到位

缺点：

- 对当前阶段偏重
- 很容易拖慢 MVP

### 结论

采用 **方案 B：本地游客 + 轻后端**。

## 5. 总体架构

### 前端

- 首次进入时检查本地会话
- 没有会话就自动创建游客身份
- 把游客身份缓存到本地
- 页面状态继续用 `localStorage` 做草稿和临时保存

### 后端

- 只负责创建游客用户
- 只负责维护 session
- 提供当前用户信息查询
- 为后续邮箱登录预留升级接口

### 数据库

最小只需要两张表：

- `users`
- `sessions`

后续再扩展：

- `works`
- `favorites`
- `progress`

## 6. 最小接口

### `POST /api/auth/guest`

创建或恢复游客身份。

返回：

- `user`
- `session`

### `GET /api/me`

查询当前身份。

返回：

- 当前用户信息
- 当前会话状态

### `POST /api/auth/logout`

退出当前会话。

说明：

- 只清理服务端 session
- 前端本地缓存可以选择保留或清空

## 7. 数据结构

### `users`

- `id`
- `type`：`guest` 或 `email`
- `created_at`
- `updated_at`

可选扩展字段：

- `display_name`
- `avatar`
- `email`

### `sessions`

- `id`
- `user_id`
- `expires_at`
- `created_at`
- `revoked_at`

### 以后再扩展的业务表

- `works`
  - 作品信息
  - 归属用户
- `favorites`
  - 收藏关系
- `progress`
  - 学院进度、关卡记录、解锁状态

## 8. 数据流

### 首次进入

1. 前端启动
2. 检查本地是否已有 session
3. 如果没有，调用 `POST /api/auth/guest`
4. 后端创建游客用户和 session
5. 前端保存本地身份
6. 页面继续正常使用

### 再次进入

1. 前端读取本地 session
2. 调用 `GET /api/me`
3. 后端确认 session 有效
4. 前端恢复当前身份和用户状态

### 后续升级到邮箱登录

1. 游客点击邮箱登录
2. 创建或绑定邮箱账号
3. 迁移游客数据到新账号
4. 保留原有作品、进度和收藏

## 9. 前端接入方式

当前前端已经有 `globalStore`，所以最小改动方式是：

- 保留现有本地 `userId`
- 新增一个 `authState`
- 在 `init()` 时优先向后端同步游客身份
- 如果后端不可用，仍然允许前端先本地运行

建议把前端身份逻辑拆成三层：

### 1) 本地草稿层

保留现在的 `localStorage`。

用途：

- 让用户立刻可用
- 让草稿和临时状态不丢

### 2) 会话层

保存后端下发的游客 session。

用途：

- 跨页面识别同一个用户
- 未来可跨设备恢复

### 3) 用户层

统一抽象为当前用户。

用途：

- 无论是游客还是正式账号，页面都只读这一个用户对象

## 10. 与现有代码的关系

### `jiu-app/stores/globalStore.ts`

这里是当前最关键的接入点。

建议：

- 保留现有本地存储逻辑
- 把 `jiu_user_id` 改为“本地游客标识”
- 让 store 未来支持服务端 session

### `jiu-app/app/layout.tsx`

这里继续负责初始化：

- 初始化游客身份
- 控制 onboarding
- 渲染全局导航和陪伴组件

### `jiu-app/app/workshop/page.tsx`

后续可以把作品保存从纯本地扩展到服务端。

### `jiu-app/app/community/page.tsx`

后续可以把“我的作品”和“社区作品”统一为云端数据来源。

## 11. 后端实现建议

如果你打算走阿里云 FC Web 函数，这一版的后端适合这样拆：

- `auth` 模块：游客创建、会话校验、退出
- `user` 模块：当前用户信息
- `session` 模块：session 读写和过期控制

数据库可先用：

- PostgreSQL

原因：

- 结构简单
- 后续适合做用户、作品、进度和关系表
- 方便以后扩展邮箱账号

## 12. 风险与边界

- 如果只做本地游客，不接后端，后续升级成本会升高
- 如果一开始就做完整登录，会拖慢 MVP
- 如果游客 session 设计不统一，前端和后端会各自维护一套身份，后面容易乱

因此这一版必须坚持：

- 游客身份先统一
- 会话先统一
- 数据归属先统一

## 13. 验收标准

满足以下条件，就算游客模式跑通：

- 用户首次打开应用会自动获得身份
- 关闭页面后再打开，身份仍可恢复
- 作品和进度能绑定到同一个身份
- 现有前端功能不被破坏
- 后续可以在不重做前端的情况下接入邮箱登录
